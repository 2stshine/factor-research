# 팀알파 팩터 연구 구조 v2 설계

작성일: 2026-10-01 · 상태: **설계 제안, 아직 미구현·미실행**

후속 상태: 사용자의 실행 승인 후 [데이터·레짐·룩백 선행 검토](research-v2-data-regime-review.md)와 독립된 준비 검사·레짐 shadow까지 진행했다. 이 문서의 전체 v2 런타임이나 여섯 팩터 연구가 구현·실행됐다는 뜻은 아니다. 최신 데이터 능력과 shadow 제안은 후속 문서를 우선 참조한다.

## 1. 결론

새 연구는 **빈 실증 기억에서 시작하되, 연구 기록은 지우지 않는다.** 한 번의 연구를 단일 팩터 단위로 유지하면서, 개발 구간에서는 명시적으로 배우고, 검증 구간에서는 정의·기억·판정 기준을 동결한다. 교훈은 좋은 이야기가 아니라 출처·적용 조건·반례가 붙은 재사용 가능한 주장으로 저장한다.

이 문서는 네 논문의 구성요소를 우리 연구 제약에 맞춰 결합한 **독자적인 설계 제안**이다. 이 조합이 성능상 최적이라는 실험적 증거는 아직 없다. 우선 통계적 정직성·재현성·학습 효율을 확보하고, 단순한 구조보다 실제로 나은지를 단계별 비교로 확인한다.

| 결정 | v2 기본값 | 이유 |
| --- | --- | --- |
| 과거 교훈 | 활성 실증 기억에 자동 승계하지 않음 | 품질·프로토콜 차이에 따른 초기 편향 방지 |
| 최근 단일 팩터 교훈 | 마찬가지로 자동 승계하지 않음 | 최근이라는 사실과 검증된 재사용성은 다름 |
| 과거 원자료·실패·노출 기록 | 읽기 전용으로 보존 | 중복 시도, 선택 편향, 이미 본 OOS를 숨기지 않음 |
| 연구 단위 | 하나의 경제적 가설, 하나의 동결된 단일 팩터 | 해석·반증·귀속이 가능한 최소 단위 |
| 개발 중 개선 | 허용된 개발 데이터 안에서 새 자식 trial로 허용 | 경험으로 배우되 실패한 실험을 덮어쓰지 않음 |
| 검증 중 개선 | 금지 | 기억·수식·파라미터·기준을 바꾸면 새 연구 |
| 에이전트 보상 | 올바른 연구 수행·근거 있는 판단 | 높은 IC·승인 개수 자체를 보상하지 않음 |
| 지식 그래프 | 출처·의존 관계를 보여주는 읽기 모델 | 그래프 연결 수가 증거 강도나 인과성을 뜻하지 않음 |
| 기억의 효용 학습 | 초기에는 관측만, 순위 반영은 나중 | 불안정한 보상으로 검색 품질을 망치지 않음 |
| 팩터 승인과 매매 | 별도 권한·검증 | 연구 승인과 실전 사용 승인은 같은 일이 아님 |

읽는 순서: 이 문서 → [구현 계약](research-v2-contracts.md) → [논문 반영 근거](research-v2-paper-review.md).

## 2. 현재 구조에서 유지할 것과 바꿀 것

현재 저장소의 `engine/epochs.py`, `engine/factors.py`, `engine/gate.py`, `engine/boundaries.py`, `engine/scientist_review.py`에는 정의 해시, 캠페인 경계, 자동 판정, 증거 연결 등 재사용할 기반이 있다. 월초 체결 비교 계약과 실제 입력 준비 코드도 이미 있으므로 전부 재작성할 필요는 없다.

반면 다음은 바꿔야 한다.

- **교훈의 평탄화:** 결과 요약, 측정 사실, 추정 원인, 일반화된 교훈을 별도 자료형으로 분리한다.
- **조회용 그래프:** 현재 연구지도는 주로 표시·검토용이다. 다음 실험의 실제 검색, 사용 기록, 수정 이력과 연결해야 한다.
- **선택적 계보 기록:** 기억을 읽었다고 선언하는 수준을 넘어 실제 주입한 기억·버전·범위를 동결한다. 이것도 에이전트가 내적으로 의존했다는 인과 증명은 아니다.
- **개발과 검증의 혼재:** 적응적 개발을 정식으로 인정하고, 그 뒤의 검증에는 별도 접근 권한을 둔다.
- **자동 발행 위험:** 현 `scripts/research.py`에는 옵션에 따라 reveal 후 Gold 발행까지 이어지는 경로가 있다. v2에서는 결과 공개와 발행을 별도 명령·권한으로 분리한다.
- **기간 계약 일관성:** 구형 전략 설정의 문서 기반 기간 해석 대신, 기간·데이터 목록이 없으면 실행을 거부하는 명시적 계약을 공통으로 사용한다.

이번 검토는 코드와 공개 상태·노출 메타데이터를 대상으로 했다. RDS의 현재 입력을 다시 인증하거나, 봉인된 성과 결과를 열거나, 새 팩터를 실행하지 않았다. 기존 작업 중인 파일도 변경하지 않는다.

## 3. 전체 흐름: 연구는 배우고, 판정은 동결한다

| 단계 | 하는 일 | 남기는 것 | 바꿀 수 없는 것 |
| --- | --- | --- | --- |
| 연구 프로그램 | 질문·예산·사용 데이터·검증 방식 결정 | ProgramPlan | 공개 후 과거 계획을 소급 수정하지 않음 |
| 단일 팩터 설계 | 메커니즘·대안 설명·반증 조건 작성 | DesignContract | 결과를 본 뒤 같은 계약의 가설을 바꾸지 않음 |
| 개발 실험 | 허용된 데이터로 평가·진단·자식 연구 | Run + EvidenceBundle | 모든 시도·실패 기록 |
| 교훈 검토 | 관찰과 해석 분리, 제한된 확인 | Claim + MemoryRevision | 원래 결과와 과거 기억 버전 |
| 공동 동결 | 여러 프로그램의 최종 후보와 판정 규칙 확정 | ReleaseGroup | 후보·기억·평가 코드·검증 기간 |
| 고정 검증 | 지정 구간을 한 번 평가하고 공개 | ValidationDecision | 공개 후 동일 검증으로 후보를 개선하지 않음 |
| 라이브러리·전략 | 연구 승인, SQL 재현, 별도 전략 계약 | LibraryEntry / StrategyTrial | 승인 근거 등급·사용 범위 |

동시에 실행하는 연구들은 같은 기억 스냅샷으로 시작한다. 배치가 닫힌 뒤 검토된 교훈을 일괄 반영한다. 먼저 끝난 실험의 결과가 뒤에서 실행 중인 실험에 몰래 섞이지 않는다.

초기에는 동시 단일 팩터 실험을 최대 3개로 제한한다. 이 숫자는 논문에서 검증된 최적값이 아니라 비용·검토 가능성을 고려한 운영 제안이다.

### 개발 단계의 적응을 어떻게 허용하는가

현행 연구 규칙보다 의도적으로 유연하게 만드는 지점이다. 예를 들어 개발 실험에서 회계 공시 시차가 의심되면, 원래 trial을 종료하고 원인을 검토한 뒤 새로운 정의와 반증 조건을 사전등록한 자식 trial을 만들 수 있다. 이전 실패는 그대로 남는다.

허용되지 않는 것은 결과가 좋아질 때까지 몰래 수식을 바꾸거나, 사후에 좋은 하위 기간만 골라 처음부터 목표였다고 쓰는 것이다. 숨긴 OOS와 전략 테스트 구간을 개선 재료로 쓸 수도 없다. **이 완화는 v2 구현·규칙 변경 이후에만 적용하며 현재 규칙을 즉시 대체하지 않는다.**

## 4. 한 번의 단일 팩터 연구는 이렇게 한다

### 4.1 결과보다 먼저 질문을 만든다

예시 질문은 “공개 가능한 시점의 특정 수익성 지표가 이후 1개월 횡단면 수익률을 설명하는가?”다. “IC가 가장 높은 수익성 수식 찾기”와 다르다.

계약에는 다음을 먼저 적는다.

1. 지표가 무엇을 측정하는지, 경제적 행동과 가격에 어떻게 연결될 수 있는지.
2. 정보의 공개·가용 시점, 모집단, 월별 신호·수익률 구간, 예상 방향.
3. 대안 설명: 규모·업종·유동성·이상치·시점 오류 등 무엇이 결과를 대신 설명할 수 있는지.
4. 주된 검정 하나, 필요한 진단, 탐색용 진단, 반증 조건.
5. 데이터·코드·전처리·비용·판정 규칙 버전, 자식 실험 수와 종료 예산.

모든 경제적 연결을 실제로 측정할 수 있는 것은 아니다. 데이터가 없는 연결은 “측정하지 못함”으로 남긴다. 미래 회계 지표 같은 결과 변수를 신호 입력에 혼입하지 않는다.

### 4.2 평가 결과는 먼저 사실로 기록한다

결정론적 평가기가 수치와 오류를 만들고, distiller는 최종 승인 여부에 대한 서사를 붙이기 전에 사실을 정리한다. 원시 실행 로그·설정·측정 결과·오류가 근거이며, 숨겨진 사고 과정을 저장할 필요는 없다.

필수 진단은 입력 결측·이상치·단위·PIT 정책·표본 이탈, 사전등록한 IC와 기본 성과, 구현 검증이다. 규모·업종 중립화, 거래활동, 국면별 결과 등은 계약에 필요·선택 여부를 명시한다. 빠진 진단을 수행한 것처럼 해석해서는 안 된다.

### 4.3 해석은 지지 설명과 반대 설명을 함께 남긴다

분석자는 가능한 해석을 작성하고, 독립 검토자는 근거 부족·대안 설명·잘못된 일반화를 찾는다. 기본 검토는 최대 두 차례로 제한한다. 합의가 안 되면 불확실성을 남긴다. 에이전트 세 명의 동의는 독립된 세 개의 실험이 아니다.

각 trial에서 교훈은 **0개부터 최대 3개**까지 만들 수 있다. “실패했으니 교훈 세 개”를 강제하지 않는다. 좋은 음성 결과도 가치 있지만, 원인을 알아내지 못한 실패는 원인을 알아내지 못했다고 적는다.

가상의 예:

| 층 | 적절한 기록 |
| --- | --- |
| 관찰 | 특정 개발 표본에서 원래 IC보다 업종 중립화 IC가 작았다. |
| 해석 | 업종 노출이 결과의 일부를 설명할 가능성이 있다. |
| 미확인 대안 | 결측 처리나 특정 시기 집중의 영향은 아직 분리하지 못했다. |
| 재사용 교훈 | 같은 지표 계열을 연구할 때 업종 중립화를 사전등록 진단에 포함한다. |
| 쓰면 안 되는 결론 | 이 계열 팩터는 업종 효과일 뿐이며 앞으로도 효과가 없다. |

### 4.4 다음 연구는 최고 점수만 보고 고르지 않는다

다음 실험은 미해결 질문, 반증 가능성, 데이터 준비도, 기존 시도와의 차이, 사전 예산으로 선택한다. 승인 가능성이 낮아도 중요한 측정 오류를 가르는 실험은 우선할 수 있다. Chair는 다음 계약을 배정할 수 있지만 판정 기준·원래 결과·OOS 권한을 바꿀 수 없다.

## 5. 기억과 지식 그래프

세 층을 구분한다.

| 층 | 예 | 수정 방식 |
| --- | --- | --- |
| 불변 증거 | 계약, 입력 해시, 코드 버전, 결과, 오류 | 덮어쓰기 금지. 새 실행·정정 증거 추가 |
| 버전 있는 해석 | 주장, 교훈, 적용 조건, 반례 | 새 revision으로 대체하고 이전 버전 보존 |
| 다시 만들 수 있는 뷰 | 검색 색인, 연구지도, 다음 연구 목록 | 원천 기록에서 재생성 |

기본 연결은 `Trial → Artifact → Observation → Claim → MemoryItem → RetrievalReceipt → 다음 Trial`이다. 문헌과 데이터 계약도 각각 주장·실행에 연결한다. 같은 결과를 요약한 보고서 다섯 개가 있어도 실증 근거의 뿌리는 하나다.

그래프에는 지지·반박뿐 아니라 “관련 있음”, “여기서 파생됨”, “이 조건에서만 적용됨”을 구분한다. 관련성이나 계보를 따라 지지 강도를 전파하지 않는다. 데이터·기간·종목이 겹치는 실험은 의존성을 표시한다. 출처 그래프는 자동으로 인과 그래프가 되지 않는다.

검색은 먼저 권한·시점·프로토콜·적용 범위로 거른 후 의미 유사성을 계산한다. 그 뒤 필요한 연결과 반례를 가져온다. 초기 기본값은 후보 20개, 최종 교훈 최대 3개, 약 1,500~2,000 실제 토큰이다. 부족하면 별도 근거 조회를 기록한다. 이 값들도 성능 검증 전의 운영 기본값이다.

매번 실제 전달한 기억, 버전, 검색·효용 스냅샷, 제외 이유를 기록한다. 검색되지 않은 교훈을 나중에 “이 연구의 출발점이었다”고 연결하지 않는다.

## 6. 교훈은 누가 검증하고, 어떻게 고치는가

연구자는 기억을 읽고 초안을 제안할 수 있지만 활성 기억을 직접 수정하지 못한다. 별도 curator만 검토 후 기록한다. 정책과 판정 규칙은 curator도 바꿀 수 없다.

확인 작업은 무제한 재검색이 아니다. 확인할 주장, 허용 자료·쿼리, 호출·행·시간 상한을 먼저 정한다. 기본 제안은 최대 3회 읽기 확인·총 120초다. 부족하면 미확인으로 남긴다. 시간이 끝났다는 이유로 사실로 승인하지도, 유효한 팩터 평가 전체를 폐기하지도 않는다.

읽기 전용이어도 hidden OOS를 조회하면 누출이다. 따라서 허용된 원자료·스키마·타임스탬프·기존 결과·합성 fixture만 확인한다. 새 수익률 검정이나 새로운 하위 집단 탐색은 별도 등록된 진단/실험이어야 한다.

운영 규칙을 현재 환경에서 확인하는 것과 경제적 효과가 미래에도 지속됨을 증명하는 것은 다르다. 전자는 probe로 확인할 수 있지만 후자는 새 적절한 실증이 필요하다.

잘못된 교훈을 발견하면 새 버전으로 정정한다. 원증거나 구조에 오류가 있으면 의존한 기억·파생 요약을 먼저 격리하고 검색·효용·cache에서 차단한 뒤 검토한다. 과거에 그 교훈을 읽었던 사실과 과거 판정을 몰래 고치지 않는다.

## 7. 기억의 효용 학습: 무엇을 보상할 것인가

MemRL의 발상은 “관련 있어 보이는 기억”과 “실제로 도움이 된 기억”을 구분하는 데 사용한다. 그러나 높은 IC·Sharpe·승인 개수로 기억을 보상하지 않는다. 그러면 기억 시스템이 과최적화 도구가 된다.

보상은 올바른 권한 준수, 재현 가능한 완료, 주장과 근거의 정합성, 필요한 반증, 정해진 예산 내 적절한 판단으로 구성한다. 유효하게 탈락시킨 연구도 좋은 수행이다. 반대로 항상 판단을 회피하거나 쉬운 질문만 고르는 것을 높은 품질로 보상하지 않는다.

처음에는 효용을 **관측용으로만 저장**하고 검색 순위에는 반영하지 않는다. 충분한 별도 평가에서 개선을 확인한 뒤에만 제한적으로 반영한다. 의무적 안전 규칙은 효용이 낮아도 검색에서 제거하지 않는다.

여러 교훈을 함께 넣고 성공했다고 각각의 기여가 증명되는 것은 아니다. 기본 효용은 함께 사용됐을 때의 관측치다. 인과적 효용을 알고 싶으면 허용된 평가 과제에서 기억 포함 여부를 통제해 비교해야 한다. 데이터 장애처럼 판단 불가능한 결과는 실패 점수 0이 아니라 미관측으로 처리한다.

## 8. 데이터 기간과 OOS: 새 출발의 한계

기억을 초기화해도 사람과 모델의 선행 지식, 기존 연구에서 노출된 결과는 사라지지 않는다. 2026-10-01 로컬의 23개 OOS 노출 메타데이터에는 신호월 기준 2023-06~2026-06에 걸친 노출과 2026-07까지의 수익률 지원 구간이 기록되어 있다. 이는 일부 기록의 합집합이며, 다른 기간이 미노출이라는 인증은 아니다.

따라서 새로 나눈 과거 데이터는 다음처럼 부른다.

- **개발 구간:** 결과를 보며 배우는 구간. 모든 변형·시도 기록.
- **재사용 역사 구간의 고정 검증:** 후보를 먼저 동결해 비교할 수 있지만 과거 노출이 있다. 새로운 독립 OOS라고 부르지 않는다.
- **미노출 역사 검증:** 중앙 이력과 접근 통제로 실제 미노출임을 확인할 수 있을 때만 사용한다.
- **전향 검증:** 동결 이후 새로 관측되는 자료에서 확인한다. 지금 연구를 시작하는 것을 막지는 않지만 시간이 쌓이기 전에 장기 실증을 주장할 수 없다.

검증 창은 개별 팩터가 아니라 중앙에서 관리한다. 독립 검증을 주장할 해당 ReleaseGroup의 구성원을 사전에 확정하고, 그 프로그램·전략의 최종 정의와 선택 규칙을 함께 동결한다. 한 결과라도 공개되면 그 창의 노출 이력이 갱신된다. 이후 같은 기간을 쓰는 새 연구는 별도의 역사 재사용 그룹으로 허용하지만 새로운 독립 검증으로 부르지 않는다.

BY 보정과 전체 시도 기록은 유지하되, 적응적으로 수식을 찾은 모든 과정의 선택 편향을 자동으로 제거한다고 주장하지 않는다. 기존 임계값은 초기 호환 기준으로 버전 고정하고, 과거 승자에 맞춰 조정하지 않는다. 숫자 자체를 개선하려면 별도 null simulation·검정력 연구와 데이터 비열람 설계가 필요하다.

또한 두 시계를 분리한다. 시장 시점에서는 당시 공개된 입력만 쓴다. 연구 시점에서는 당시 공개·검토된 기억과 효용만 쓴다. 2026년에 배운 교훈을 활용한 2018년 백테스트는 2026년에 설계한 전략의 과거 시뮬레이션이지, 2018년에 이미 가능한 에이전트의 실적이 아니다.

## 9. 국면 분석과 월 리밸런싱은 어디에 들어가는가

### 국면은 설명 도구가 먼저다

기본 해석은 네 시장 국면과 연속형 축을 함께 보여주는 방향을 권한다. 16개 조합을 모두 팩터 승인 규칙으로 만들지 않는다. 성장·물가의 수준과 개선·악화도 같은 의미로 취급하지 않는다.

검증할 새 국면 정의의 후보는 **10개월 추세 × 일별 63거래일 실현변동성**이다. 최초 설계는 과거 확장 중앙값과 최소 24개 과거 월을 제안했다. 후속 입력 감사에서 기준 분포의 긴 기억과 워밍업을 확인해, 실제 shadow는 **현재 월을 제외한 직전 12개 연속 월의 RV63 중앙값**을 별도 버전으로 고정했다. 시장·입력별 가용성을 확인하고 부족하면 UNKNOWN으로 둔다. 두 정의를 혼동하지 않으며, shadow도 최적값으로 검증되거나 운영 채택된 것은 아니다. 상세 정의·실행 결과는 후속 검토를 따른다.

일별 가격 입력의 연속성과 가용 시점을 확인하지 못하면 이 정의를 구현 완료로 취급하지 않는다. 기존 국면과 새 국면의 식·버전·UNKNOWN 비율·전환 빈도·각 국면의 월 수를 비교하되, 팩터 수익률이 좋아지는 경계를 찾아 조정하지 않는다. 첫 기억 시스템 비교에서는 국면 정의를 고정해 변경 효과가 섞이지 않게 한다.

국면별 유효 표본은 주식 행 수가 아니라 공통 충격을 공유하는 월 수를 중심으로 판단한다. 유효 월 수, 효과 크기, 불확실성, 여러 비교를 함께 표시한다. 표본이 적으면 “효과가 없다”가 아니라 “판단할 자료가 부족하다”다. 국면별 매매 전환은 별도 전략 가설이며 사전등록이 필요하다.

기존에 받아들인 매크로 `PIT_ASSUMED` 정책은 그 표시와 한계를 유지한다. 최초 발표값을 확인한 데이터로 승격시키거나 전체 수집을 처음부터 다시 막지 않는다. 다만 전향적으로 빈티지·발표 시점 스냅샷을 남겨 검증 가능한 부분을 늘린다.

### 측정용 팩터와 매매 전략을 분리한다

- 팩터 연구의 주된 질문은 고정된 월별 점수와 다음 수익률의 관계다. 20% 동일가중은 비교 가능한 기준선으로 유지한다.
- 10%/20%와 동일가중/제곱근 시가총액 가중의 2×2 비교는 별도 전략 계약으로 묶는다. 최고 성과만 골라 팩터 자체가 더 좋다고 재해석하지 않는다.
- 전체 연구 대상의 동일가중 대비 성과는 종목 선택의 질문, 시장 총수익지수(TR) 대비 성과는 투자 대안의 질문이다. 둘 다 보여주고 혼동하지 않는다.
- 실제 매매 비교는 월말 관측 자료, 실제 `available_at`, 결정 시각, 다음 월초 체결 시각을 분리한다. 월초 시가를 쓸 경우 결정·주문 가능 시각보다 늦게 도착한 입력을 끼워 넣지 않는다.
- 배당 권리, 기업행동, 거래정지·상장폐지, 비용, 실제 거래 달력, 비교 지수의 수익률 창을 맞춰야 한다. 단순 수정시가로 총수익률이 모두 해결된다고 가정하지 않는다.

현재 월초 비교는 공식 벤치마크·기업행동 등 입력 준비가 완료됐다고 인증할 수 없다. 입력이 없으면 전략의 해당 측정을 미산출로 표시한다. 이것이 허용된 입력으로 하는 IC 연구까지 모두 중단시켜야 한다는 뜻은 아니다.

## 10. 승인 체계와 대시보드

사용자에게 보이는 팩터 결론은 **승인 / 탈락**, 미완료는 **진행 중**으로 단순화한다. 별도의 “조건부 승인”은 만들지 않는다. 하지만 증거 등급·전향 검증·사용 권한을 숨겨 승인 하나로 합치지도 않는다.

표시 예: **연구 승인 · 과거 재사용 검증 · 전향 미확인 · 실전 실행 미승인**. v2 연구 승인은 별도 `research-admission-v2` 계약으로 판정한다. 초기에는 개발 검사와 동결한 36 유효 월의 역사 검증을 요구하되, 그 자료가 재사용이면 독립 증거라고 부르지 않는다. 미래 36개월을 기다리지 않아도 된다는 말이지, 필요한 검사를 생략하거나 미실행을 PASS로 바꾼다는 뜻은 아니다. 자세한 검사 집합은 구현 계약에 고정한다.

연구 승인 후에도 별도 StrategyTrial의 입력·기간·사용 범위 계약을 통과해야 연구·모의 전략에서 활용할 수 있다. 실전 사용은 별도 승인을 요구한다. v2 연구 승인은 기존 Gold `PROMOTE`와 다른 판정이며, 이 구분은 화면 문구뿐 아니라 SQL/API/cache/전략 실행기의 필터로 강제한다.

연구지도는 다음 세 층을 기본 화면으로 보여준다.

1. **무엇을 알아보려 했나:** 경제적 질문과 사전등록된 비교.
2. **무엇을 관찰했나:** 주요 결과·입력 품질·불확실성·기존 결과와의 의존 관계.
3. **다음에 무엇이 달라지나:** 재사용 가능한 교훈 또는 아직 풀리지 않은 질문.

옛 연구는 삭제 대신 “이전 프로토콜 보관함”으로 분리한다. 기본 지도에는 v2 연구만 표시한다. 단순 결과 요약은 “결과 기록”, 검토된 적용 범위가 있는 기억은 “재사용 교훈”으로 구분한다. 최신순 정렬과 한국어 제목은 유지하되, 최근이라는 이유로 증거가 강한 것처럼 표현하지 않는다.

## 11. 구현·전환 순서

| 단계 | 구현할 것 | 다음 단계로 갈 조건 |
| --- | --- | --- |
| 0. 경계 동결 | legacy namespace, 노출·시도 목록, v2 정책·기간·데이터 계약 | 삭제 없이 재현 가능한 목록, 기존 실행에 영향 없음 |
| 1. 증거 기반 | 불변 산출물, 이벤트 저장소, 중앙 접근 중개, 전역 검증 창 | 누출·재시작·동시성 테스트 통과 |
| 2. 기억 기반 | distiller/curator, 범위 있는 주장, 검색·반례·사용 영수증 | 잘못된 교훈 수정과 시점 재생 테스트 통과 |
| 3. 작은 연구 | 3개 가설 계열 × 2개 사전 계획된 단일 팩터 비교 | 과정 완결성 확인; 6건으로 학습 효능을 주장하지 않음 |
| 4. 효용·UI | 기억 구조 비교, 선택적 효용 순위, 연구지도 연결 | 품질 개선 또는 같은 품질에서 비용 개선 |
| 5. 검증·전략 | 공통 동결, 적절한 등급의 검증, 별도 발행·매매 계약 | 데이터·증거·권한 조건 충족 |

초기 저장소는 단일 writer의 SQLite 이벤트 저장소와 내용 해시 기반 파일, 관계형 edge 테이블이면 충분하다. 그래프 DB나 복잡한 에이전트 프레임워크부터 도입하지 않는다. 향후 동시 writer가 늘면 PostgreSQL로 이동할 수 있다.

기존 Gold와 데이터는 그대로 둔다. 원하면 향후 같은 정의를 v2에서 재실행할 수 있지만 “새로운 팩터 발견”이 아니라 프로토콜 변경 재현/재검증으로 등록한다. 새 활성 기억에는 legacy 요약·임베딩·효용·파생 주장까지 기본 제외한다. 기억 초기화를 이유로 노출 원장과 누적 시도를 초기화하지 않는다.

## 12. 이 설계가 정말 나은지 확인하는 방법

처음부터 네 논문의 모든 기능을 켜지 않는다. 동일한 평가 과제와 전체 비용 한도에서 다음을 비교한다.

| 구성 | 추가 기능 | 검증 질문 |
| --- | --- | --- |
| B0 | 공통 기반만, 활성 경험 기억 없음 | 기억 없이도 충분한가? |
| B1 | 범위 있는 교훈 저장·검색 | 과거 경험을 읽는 것이 도움이 되는가? |
| B2 | 확인·수정·은퇴 절차 | 틀린 교훈의 재사용을 줄이는가? |
| B3 | 출처·반례 그래프 검색 | 복잡성 대비 근거 선택이 좋아지는가? |
| B4 | 제한된 효용 순위 | 유사성 검색보다 실제 수행이 좋아지는가? |

모든 구성에는 동일한 정책·입력 계약·문헌 접근·성과 없는 정의/시도 색인을 제공한다. 활성 경험 기억과 그 관리·검색 기능만 다르게 한다. B1에만 중복 시도 정보를 더 주는 식의 비교는 하지 않는다.

평가는 데이터 누출 탐지, 오래된 스키마 교훈 수정, 과잉 일반화 거절, 반례 검색, 재현 실패 진단, 시점별 기억 재생 등 절차적 과제에서 먼저 한다. 과제 계열 단위로 개발·최종 평가를 나누고, 에이전트·색인·효용 저장소도 구성별로 격리한다. 문구만 바꾼 같은 오류를 양쪽에 넣지 않는다.

주요 지표는 올바른 행동·판단, 근거 없는 주장, 치명적 누출, 적용 범위 준수, 수정 후 오류 재발, 재현성, 전체 토큰·시간·비용이다. 불필요한 회피도 오류로 센다. curator·probe·색인 비용까지 포함한다. 반복 실행과 순서를 바꿔 불확실성을 제시하고, 연구 6건의 좋은 결과를 구조의 우월성 증거로 삼지 않는다.

안전 조건을 어기면 해당 구성은 배제한다. 품질 차이가 불명확하면 더 단순하고 저렴한 구성을 유지한다. 최종 평가 결과를 보고 고친 구성은 같은 평가 세트에 대한 새 독립 검증으로 주장하지 않는다.

## 13. 이번 설계의 범위

네 논문의 본문·알고리즘·실험과 관련 부록, 일부 공식 구현·프롬프트, 현재 저장소의 연구·전략·기억 계약을 검토했다. 논문 실험을 재현하거나 이 설계를 실행해 우월성을 입증한 것은 아니다.

이번 산출물은 설계와 구현 계약이다. 데이터 삭제, 기존 연구 폐기, 규칙 파일 교체, 연구 재실행, Gold 발행, 사이트 배포, 커밋·병합은 수행하지 않는다. 구현은 0~2단계부터 시작하는 것을 권한다. 그 기반이 갖춰진 뒤 팩터를 다시 돌리는 것이 순서다.
